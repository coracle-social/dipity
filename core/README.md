# core

Everything below the UI, in Rust. See [`docs/overview.md`](../docs/overview.md#architecture) for why it exists and what belongs here; this file covers the build.

## Layout

| Crate | Role |
| --- | --- |
| `dip` | Protocol, crypto, store, session. Pure logic, no bindings, testable on the host. |
| `dip-ffi` | The uniffi surface. Everything crossing to Swift or Kotlin is declared here by hand. |

The split keeps binding machinery out of the code under test, and keeps the FFI surface something you have to write on purpose rather than something that accumulates.

Anything the core needs from the platform is a trait declared here and implemented by the shell — see [the call direction](../docs/overview.md#architecture). Keep that trait set small and coarse; each one is a place the core blocks on Swift or Kotlin.

Modules mirror the design documents one to one.

## Building

Every recipe lives in the [`justfile`](../justfile) at the repo root, not here.

```sh
just setup         # rust targets, pnpm deps
just core-test     # host tests
just bindings      # Swift + Kotlin from the built cdylib
just ios-lib       # XCFramework, device + simulator
just android-lib   # jniLibs, all ABIs — needs the NDK and cargo-ndk
just android-check # compile the Android shell — needs the SDK, not the NDK
just qa            # what CI runs
```

Generated output stages under `core/target/ffi/`, which is gitignored and rebuilt from scratch. Nothing generated is committed.

`just sync` chains core → bindings → web → `cap sync`, and the mobile recipes go through it, so a native build cannot pick up a stale library.

## Wiring into the native projects

Each shell references the artifacts once, from the Capacitor plugin. `just sync` puts them there; nothing generated is committed, so what a native build links against is whatever was last compiled here.

**iOS.** `ios/App/CapApp-SPM/Package.swift` is regenerated by `cap sync` and says so at the top, so the binary target does not go there. It belongs to `ios/App/DipFFI`, our own local SPM package, which declares `DipFFI.xcframework` as a `.binaryTarget` and carries `dip_ffi.swift` in its sources. `just ios-lib` writes both. The shell itself is the Swift under `ios/App/App/`, in the app target.

**Android.** `just android-bindings` writes the generated Kotlin into `android/app/src/main/` and `just android-lib` the `jniLibs/` beside it, both named as extra source sets by `android/app/build.gradle`. Neither that file nor `android/build.gradle` is regenerated by `cap sync`, so the edits there — the Kotlin plugin, the source sets, and the `net.java.dev.jna:jna:5.x@aar` uniffi's bindings need — are safe to make by hand. `variables.gradle` is applied from *inside* the `buildscript` block, because Gradle evaluates that block before the rest of the file and the Kotlin plugin version is read there. The plugin is `DipPlugin.kt` beside `MainActivity`, which registers it: a plugin in the app module is named rather than discovered.

Compiling needs the bindings but not the `jniLibs`, so `just android-check` skips the NDK: it stages the Kotlin, runs `cap sync android`, and builds a debug APK it throws away. That `cap sync` is also what writes `android/capacitor.settings.gradle`, which resolves the Capacitor module through the local `node_modules` layout and is gitignored for it — a gradle build always follows one.

### The Xcode project

Xcode compiles a list, not a directory, and `ios/App/App.xcodeproj/project.pbxproj` is the list. A Swift file on disk that it does not name is not part of the build, with no error anywhere — you get a working stock Capacitor app that answers nothing, which is what `coreVersion` rejecting is there to catch. `cap sync` does not write that file, so the four files under `ios/App/App/` and the `DipFFI` package are named in it and committed like any other source. A fresh clone needs nothing done in Xcode.

Adding a file there later is still best done in Xcode, which writes the three entries one file needs — a `PBXFileReference`, a `PBXBuildFile` and a line in the target's Sources phase — and picks the uuids. `just xcode` is what says whether the edit landed: it reads the project file and fails if a `.swift` under `ios/App/App/` is not compiled, if a local package beside it is not linked into the App target, or if any reference dangles. It is in `qa` and in CI, and it is the only thing anywhere that reads the iOS project.

Xcode 16's synchronized folder groups would make the file list automatic, and are not worth the conversion here: `ios/App/App/` also holds `public/`, the built web assets, which the bundle needs as one folder reference rather than as several hundred loose resources.

Everything else is `just ios`.

## Adding a dependency

Heavy dependencies go in `[workspace.dependencies]`, added when the module that needs them arrives so version choices stay in one place: `coracle-lib` for nostr types and negentropy, `coracle-kinds` for the reader/writer pair per event kind, `rusqlite` for the store, `secp256k1` for authorship and auth signing, `k256` for the authorship proof's explicit group arithmetic, `snow` for Noise XX.

`coracle-lib` and `coracle-kinds` are released crates, so the core builds anywhere, CI included. A git rev still would not: their `src/` is tangled from `book/` and gitignored upstream, so cargo clones the repo and finds no `lib.rs`.

Working on the library and the app at once is the commented `[patch.crates-io]` block at the bottom of [`Cargo.toml`](./Cargo.toml), which points both at a local checkout. That checkout needs `just tangle` run in it first, and anything we need there is a chapter edit — hand-editing the tangled source is lost on the next tangle. Uncomment it to iterate; comment it back out before committing, or the build stops resolving on every other machine.
